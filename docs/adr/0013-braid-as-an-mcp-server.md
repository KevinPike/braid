# braid as an MCP server: bounded spends with a human's yes, never a Sign-off or an apply

`harness-mcp` serves braid's **Workflows** as MCP tools so that another client, Claude Code for one, can drive them (`specs/skills-and-mcp.md`, F18). The client is an agent, not a human. It can read the **Catalog**, the Plans, the runs and the **Bench ledger**, and it can start a Plan, a build or a bench, which spends money. That is the part to get right: an agent that reads a hostile web page or tool result may be talked into starting runs, and a run costs real dollars. ADR 0011 and ADR 0012 take the same view of skills and of MCP servers braid connects to. Here braid is the server, so the defence is what a client, however persuaded, can reach.

## Decision

1. **stdio only, launched by the client** (`claude mcp add braid -- uv run --env-file .env harness-mcp`). Streamable HTTP would bring Origin checks and authentication for no gain on one machine. Nothing but MCP messages goes to stdout; **Workflow** progress goes to the run log and to MCP progress notifications.
2. **Reads are free, spends need a human's yes.** The model **Catalog**, Plans, runs, run status and the **Bench ledger** carry `readOnlyHint` and touch no model. `braid_plan_start`, `braid_build_start` and `braid_bench_start` start a run in the background and return its id. Before any of them starts a run, braid asks the client's human through **MCP elicitation**: a yes/no that states the model, the **Spend cap** and what is left of the day, plus, for a build or a bench, what the **Bench ledger** says such runs cost. A decline, a cancel or a client that cannot elicit starts nothing.
3. **A weaker mode exists and says so.** `[mcp_server] confirm = "token"` is for clients without elicitation: the first call returns a quote and a single-use token, bound to the tool and its exact arguments and valid for five minutes; the second call, carrying the token, starts the run. It relies on the client's agent to confirm with its user, which braid cannot check. It is off by default and the quote says so.
4. **Two ceilings clamp every spend.** `max_cost_usd` caps one started run and `daily_cost_usd` caps all MCP-started runs since local midnight, summed from the run index, where a running run counts at its cap so that concurrent grants cannot overshoot. The client's request is clamped to the smaller figure and the clamp is reported. A spending call is refused, before anyone is asked, when the day's ceiling is used up. The granted figure becomes the run's **Spend cap** in `WorkflowConfig.max_cost_usd`, which the Workflow already enforces at each node boundary (a bench's figure is its bench-wide cap). braid does no cost accounting of its own.
5. **Human pauses become `waiting`.** A run that stops for a human (a Plan review, a clarify, **Stuck**) keeps its state and reports `waiting` with the payload and how to continue. `braid_run_answer` answers those three; it re-clamps the run to what the daily ceiling still allows, because an answer lets the run spend again. The route an answer decides is a **Route record** with basis `mcp-client` (ADR 0008), so a trace tells a client's answer from a human's. **Sign-off** and the finish, which applies the diff, are never answered over MCP: the run ends at that **Checkpoint** with status `waiting`, and a human resumes it in the TUI (`/build --resume <run-id>`). Nothing in the server applies a diff.
6. **Keys stay in the environment.** `ANTHROPIC_API_KEY` and `OPENROUTER_API_KEY` are read as the CLI reads them. Every string that leaves the server, a result, an error, a progress message or a log record, passes the `sk-` redaction that ADR 0009 and ADR 0012 use and has the exact key values removed. Only the Anthropic backend is on by default; `backends = ["anthropic", "openrouter"]` adds OpenRouter, and the frozen Ollama path (ADR 0007) is never offered.
7. **Runs are the usual runs.** They are `build_plan_graph` and `build_execution_graph` driven by `drive_graph` over the SQLite checkpointer, recorded in the same run index (`origin = "mcp"`, with cost and cap), so the TUI's `/runs` lists them and can resume one. Code a model wrote still runs only in the **Sandbox** (ADR 0005).

## Considered options

- **Let a run that needs a human fail.** Rejected. A run stopped for a hint is most of its value; `waiting` keeps it and lets the client or a human continue.
- **Let the client give Sign-off, or apply the diff.** Rejected. Sign-off is the human's judgement that the feature works, and applying the diff is the one step that changes the project. An agent that has just read untrusted text must not reach either (ADR 0005 moved approval to the diff for this reason).
- **Trust the client's own confirmation.** Rejected as the default. The client's agent is the party that may have been persuaded. It is kept as an explicit weaker mode for clients that cannot elicit.
- **One ceiling.** Rejected. A per-run cap alone lets a loop of small runs spend without limit; a daily one alone lets one run spend the day.
- **A separate run index for MCP runs.** Rejected. The point of `waiting` is that a human can pick the run up in the TUI.

## Consequences

- With `confirm = "elicit"`, a client without elicitation cannot start a spend at all. That is intended.
- The TUI and `harness-mcp` share `workflows.db`. The checkpointer writes on the same event loop that updates the index, so the server gives its index connection a short busy timeout and retries a locked write between awaits instead of blocking the loop on SQLite's lock. A run is owned by the process that started it: after that process exits, a `waiting` run is resumed from the TUI only.
- Cancelling a run cuts the node in flight (and its HTTP stream); the run resumes from its last **Checkpoint**, which is the last node boundary.
- The daily ceiling counts what MCP-started runs recorded in the index. Runs started from the TUI, and the Anthropic key's own limits, are not part of it.
- A plan run, which the client may approve, saves a Plan and nothing else; it changes no project file until a human builds it and applies the diff.
